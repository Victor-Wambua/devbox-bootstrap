Write your own profile

A profile is a plain text file. It says what a machine should look like; devbox works out what to do. You can start from an existing one, or capture your current laptop with devbox export.

Where profiles live

devbox looks for NAME.conf in these places, and the first match wins:

  1. Each directory in $DEVBOX_PROFILE_PATH (colon separated).
  2. ~/.devbox/profiles/
  3. The profiles/ directory that ships with devbox.

So a team can keep its profiles in a git repo, point DEVBOX_PROFILE_PATH at a checkout, and even override a bundled profile by reusing its name.

A first profile

# ~/.devbox/profiles/team-web.conf
summary: "What our web team installs"
include: base node

formula postgresql@16 min=16.0 why="Matches production"
cask    docker bin=docker

block   team-env file="~/.zshrc" line="export COMPOSE_PROJECT_NAME=web"
cmd     clone-monorepo run="git clone git@github.com:example/web.git ~/code/web" check="test -d ~/code/web/.git"

Then:

devbox plan --profile team-web      # what would change, and the exact commands
devbox apply --profile team-web     # make it so (asks first)
devbox doctor --profile team-web    # what has drifted since

The format

One directive per line. A line is either a header (summary: or include:) or a step: a kind, an id, then key=value options. Use double quotes around values that contain spaces. Inside quotes, \" and \\ are the only escapes. # starts a comment at the start of a word.

The parser never evaluates anything. $HOME, backticks and $( ) inside a value are kept as literal text; they only run if you put them in a cmd or check string, which devbox runs with bash -c after showing it to you in the plan.

Step kinds

formulaid onlybinminversionargwhyInstalls a Homebrew formula. Doctor also checks the binary is on PATH and meets min.

serviceid onlystartwhyA Homebrew service. With start=yes apply starts it; otherwise it is only checked by doctor.

cmdrunchecksudowhyRuns a command. check decides if it is already done and must be read-only. sudo=yes lets it prompt.
blockfilelinewhyOwns a marked region of a file under your home directory, one line= option per line.
defaultsdomainkeytypevaluerestartwhySets one macOS preference. The previous value is saved to a restore script first.
vscodeid onlywhyInstalls a VS Code extension by id.
uvpythonid onlywhyInstalls a Python version with uv.
installerurlsha256runcheckwhyDownloads from an https URL, verifies sha256, then runs it. Needs --yes.

Rules that keep profiles safe

  • Every step needs a way to tell it is done. Built-in kinds have one. For cmd, the check must be read-only and exit 0 only when the work is already done. Apply re-runs the check afterwards, and a step that does not pass it is reported as failed.
  • Blocks only touch your home directory. file must start with ~/ and may not contain ... Block ids are unique per profile set; two profiles that define the same step identically are merged, and conflicting definitions are an error.
  • Profiles are code. A cmd runs with your privileges. Read a teammate's profile as you would read a script, and read the plan before you apply it.
  • Upstream installers are a last resort. An installer step downloads over https, verifies a pinned sha256 and only then runs the file. It is never run without --yes. None of the bundled profiles uses one.
  • Prefer Homebrew steps to cmd where you can: they are checked, listed in the Brewfile and shown by doctor with versions.

Managed blocks

A block step owns this region of the file, and nothing else in it:

# >>> devbox:team-env >>> managed by devbox; edits between the markers are overwritten
export COMPOSE_PROJECT_NAME=web
# <<< devbox:team-env <<<

If the block is missing, apply appends it once. If its content differs from the profile, apply replaces it in place. If the markers are unbalanced or duplicated, devbox marks the step blocked and changes nothing. Before any file changes, the original is copied to ~/.devbox/backups/<time>/files/.

Test a profile safely

  1. devbox list --profile team-web parses it and shows the resolved steps, with no machine access.
  2. scripts/try.sh -- plan --profile team-web runs devbox against a throwaway mocked machine: temp HOME, mock brew, nothing real.
  3. devbox plan --check --profile team-web exits 4 while anything is pending, which makes a cheap drift check in CI or a login script.

Exit codes

CodeMeaning
0Success. For doctor: no failures (warnings allowed).
1A step failed, or doctor found failures.
2Bad flags, or a manifest that does not parse or has an include cycle.
3Refused by a safety rule: root, not macOS, no --yes, Homebrew missing.
4plan --check found changes pending.
